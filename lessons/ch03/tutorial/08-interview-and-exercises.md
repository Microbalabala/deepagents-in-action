# 08｜面试追问、系统设计与练习答案

复习顺序：先用两分钟解释架构，再用实验结果证明关键语义，最后讨论并发、隔离、恢复与成本。面试中的好答案应包括“适用前提”，而不是无条件评价哪个 Backend 最好。

## 1. 两分钟讲清虚拟文件系统

参考回答：

“Deep Agents 用文件工具为模型提供按路径访问资料的能力，底层由可插拔 Backend 实现。模型不用每轮携带全部材料，可以先检索再分页读取，将中间结果保存为文件。工具层处理参数、权限和返回格式，Backend 决定内容存在 State、磁盘还是 Store。

StateBackend 的文件属于线程图状态，多轮保存依赖 Checkpointer；Filesystem 的共享范围取决于实际根目录；Store 的共享范围由 Store 实例及 namespace 决定。Composite 可以将任务草稿与长期资料按路径分流。

我用相同的 A 写入、A 读取、B 读取流程比较了 State 和 Filesystem，再通过独立实验观察 Store 的 namespace 以及 Composite 路由。我还运行了七种文件工具，并在选学实验中观察了大结果卸载和权限拒绝。生产上还需要身份与线程授权、并发控制、持久化和审计，因为文件抽象本身不会自动提供这些保证。”

这段答案应结合自己实际跑过的实验展开，不必逐字背诵。

## 2. 基础与机制：问题 1–10

### 问题 1：为什么要使用文件系统，而不是直接增大上下文窗口？

更大窗口缓解容量问题，但不自动解决资料组织、重复输入、证据定位和成果复用。文件系统把资料变成可寻址对象，结合索引和按需读取控制当前输入规模。代价是增加工具调用与检索管理，需要防止读错文件和引用过期。

追问：如果每次都读全部文件呢？收益会减少甚至变差，还增加 I/O。应测实际请求 token 与任务完成率，而不是只统计保存了多少文件。

### 问题 2：虚拟文件系统是不是操作系统 VFS？

不是完整 POSIX 文件系统实现。它是 Agent 工具的一套路径与内容协议；StateBackend 里的文件可以只是状态键。不能推断存在 inode、锁、原子 rename 或事务。

### 问题 3：工具调用是谁执行的？

模型生成结构化请求，编排框架找到工具执行函数，中间件校验权限和参数，Backend 访问存储，结果转为 ToolMessage 返回模型。模型说“我写好了”不等于外部副作用已经发生。

### 问题 4：State 中保存文件，会不会全部进入 prompt？

不会仅因为存入 `files` 就全部进入模型请求；一般需要通过工具读取。但文件仍可能进入检查点序列化，所以模型输入成本与状态保存成本要分开计算。

### 问题 5：StateBackend 是临时的，是否意味着进程重启必然丢失？

不必然。配合持久化 Checkpointer 恢复同一线程时，可以恢复文件。临时通常强调线程作用域和用途，不是所有部署下都只存在 RAM。本文实验的 InMemorySaver 确实不能抗重启。

### 问题 6：为什么只传 thread_id 还不够？

thread_id 是检索线程状态的标识，不是存储服务。需要 Checkpointer，或由应用显式管理状态。还必须验证当前用户是否有权访问该线程。

### 问题 7：Checkpointer 和 Store 有什么区别？

Checkpointer 保存图状态和执行恢复信息，以线程为作用域；Store 保存独立应用数据，可以跨线程共享。常见组合是前者保留任务进度，后者保存用户长期偏好。两者都需要选择合适的持久化实现。

### 问题 8：StoreBackend 为什么不一定长期持久化？

Backend 是访问 Store 的文件适配层；InMemoryStore 仍在内存中。跨线程可见与跨进程耐久是不同性质。

### 问题 9：`offset=100, limit=50` 读取哪部分？

对文本是从第 101 行开始最多 50 行。offset 为 0 基，而展示行范围常为 1 基。真实返回还可能受内容长度限制，应检查下一偏移量与截断提示。

### 问题 10：grep 计数为 10，能否断言关键词出现 10 次？

不能。它通常统计匹配行/记录，同一行可能出现多次；如果搜索截断，计数还只是已返回部分。业务计数需要专门定义统计对象和完整性条件。

## 3. API 与排障：问题 11–18

### 问题 11：write_file 和 edit_file 应该怎么选？

本版本 write_file 创建或完整覆盖，适合生成新产物或有意重写全文件；edit_file 做精确局部替换，遇到多处匹配默认拒绝。二者都不是并发安全的业务事务接口。

### 问题 12：为什么不能在普通 Python 顶层直接调用 StateBackend.write？

本版本从 LangGraph 执行上下文读取和更新 files 通道，顶层没有这些运行时信息。可以通过实际图工具链调用，或在 invoke 输入中预置符合本版本结构的 files；不要通过私有 API 伪造运行环境。

### 问题 13：旧代码的 `backend=lambda rt: ...` 为什么失效？

本课程基线要求直接传 Backend 实例；动态 namespace 工厂仍然存在，因为它计算运行时隔离键，不负责创建后端。两种 lambda 用途不同。

### 问题 14：后端读到了内容，但工具展示不同，是谁的问题？

先区分后端结构化结果与中间件展示处理。工具可能添加分页头、裁剪长内容、转换多模态或过滤权限。逐层记录输入输出，比在最终字符串上盲目修补更可靠。

### 问题 15：glob 与 grep 为什么可能“成功但不完整”？

搜索可能受到时间、数量或遍历预算限制，并返回已找到的有效部分，同时标注 truncated。应用应缩小范围继续查询；不能把 success 解释成遍历了全部数据。

### 问题 16：文件被卸载后，Agent 为什么仍不知道某条事实？

可能只看了预览，没有回读中间证据，或检索关键词不匹配。卸载提供可寻址保存的机制，不保证模型自动检索成功。可以给实验 08 增加一条位于正文中间的特殊证据，再要求模型回读，作为后续检索能力实验；新版基础脚本只验证保存完整性。

### 问题 17：20,000 token 卸载阈值是否精确？

本版本该工具结果路径使用字符数近似，不能当作精确 tokenizer 结果。多种消息类型的裁剪与卸载策略也不同。真正成本应读取模型 usage，并处理缓存与其他计费维度。

### 问题 18：自定义模型小窗口，摘要为什么没及时触发？

先检查模型 profile 是否包含有效 max_input_tokens。缺失时可能使用固定回退阈值，不能自动知道自定义服务的真实容量。需要明确配置摘要策略并测实际请求大小。

## 4. 安全与系统设计：问题 19–28

### 问题 19：virtual_mode=True 是不是完整沙箱？

不是。它提供相应文件操作的虚拟路径语义和约束，不能隔离任意代码执行。LocalShell 命令在宿主机运行，需要真实进程/容器隔离才能约束执行能力。

### 问题 20：namespace 隔离后，能否不用线程授权？

不能。错误复用 thread_id 可能泄露已经保存的聊天与工具结果，即使当前 Store 查询已隔离。必须同时控制线程状态、文件存储和检索索引的访问。

### 问题 21：为什么拒绝 write 还要考虑 delete 和 upload？

文件生命周期有多个写入口。目录删除可以移除受保护后代，上传可以覆盖文件，执行工具也可能绕开文件工具。策略必须覆盖实际入口，不能只按某一个工具名称设计。

### 问题 22：拒绝规则先写还是允许规则先写？

在 first-match-wins 规则中，一般将具体例外放在前，最后放兜底策略。是否默认拒绝取决于配置；本版本无匹配默认允许。必须测试规则交集、父目录与路径规范化。

### 问题 23：CompositeBackend 是否能跨多个存储原子提交？

不能据路由功能推断事务。写草稿成功、写长期索引失败可能产生半完成状态。可以先写不可变对象，再提交 manifest/完成标记，或使用应用层事务协调和补偿。

### 问题 24：多任务同时 edit 同一个文件怎么办？

先确定冲突策略：单写者、版本条件更新、事务内 read-modify-write 或业务合并。普通读后替换再覆盖可能丢失更新。第 06 部分用版本条件演示了拒绝过期写入。

### 问题 25：如何保证恢复时不重复副作用？

将操作绑定稳定幂等键，记录已完成状态，对覆盖写使用版本前提；对发布、通知等外部副作用使用独立幂等提交协议。图恢复不自动让外部存储与检查点形成分布式事务。

### 问题 26：多 Agent 共享文件能解决协作问题吗？

它提供交换产物的通道，但不解决执行顺序和并发覆盖。共享状态与文件更新的传播取决于子图编排；外部 Store/磁盘共享也只说明访问同一存储。更可靠的设计是每个任务写自己的产物，汇总者在完成信号之后读取固定版本。

### 问题 27：文件中出现“忽略权限”的指令怎么办？

将其作为不可信资料处理，不让它改变系统目标或授权。再由实际权限、身份和执行环境阻止越权。模型层的指令遵循与系统层授权是互补的。

### 问题 28：怎么证明一个研究 Agent 是可靠的？

同时测工具正确性、存储语义、检索召回、引用可解析性、断言支持率、任务完成率和故障恢复。按真实使用分布构造任务集并做重复实验，不能用一个漂亮答案证明可靠。

## 5. 进阶追问：问题 29–32

### 问题 29：一百万份文件，grep 还能作为主要检索方式吗？

全量扫描通常会成为成本与延迟问题。应引入权限感知的索引、分区和范围过滤，必要时混合语义检索。原文仍是证据源，索引结果需要映射到版本固定的文件；索引滞后与删除同步必须处理。

### 问题 30：文件分页中间被修改，结果会怎样？

offset 指向的位置可能变化，导致重复或遗漏。要得到一致证据，应读取不可变版本或在每次分页前验证版本/ETag，不一致则重新开始。只保证 next_offset 单调递增不够。

### 问题 31：为什么摘要不能代替原始证据？

摘要有损且可能包含错误归纳。关键数值、授权和冲突结论应回到权威状态或原文验证。摘要更适合导航、进度和约束提示，而不应成为不可核验的事实终点。

### 问题 32：你如何选择 Backend？

先拆需求：临时任务状态、跨任务共享、进程恢复、租户隔离、文件规模、执行代码和延迟目标。再选择存储与隔离方案。常见组合是 State 保存小型任务数据、持久化 Store 保存用户信息、大原文放外部存储、需要执行时使用沙箱，并由路由统一工具视图。

## 6. 系统设计题：多租户研究平台

**题目：** 有 10,000 个用户，每个用户最多同时运行 5 个研究任务。每个任务读取 50 份材料，平均每份 200 KB。需要跨任务偏好、任务恢复和可追溯报告。请设计存储与上下文系统。

### 6.1 先估数量级

若粗略按每用户 5 个任务计算，共 50,000 个任务；每任务约 10 MB 原文，总逻辑原文量约 500 GB。这里使用十进制 KB/GB 估算，未计副本、检查点、元数据、索引和清洗版本。

这不意味着所有任务同时读取全部资料，也不意味着每份原文都应复制进检查点。估算的目的，是识别“大原文放 State”可能带来的放大问题。

### 6.2 明确访问模型

用户只能访问自己的任务和授权共享资料。thread_id 必须由服务端绑定用户。偏好 namespace 包含 tenant 和 user；任务草稿包含 task_id。公共资料允许内容去重，但私有授权映射必须保留，不能因为哈希相同就暴露用户存在性。

### 6.3 存储拆分

- Checkpointer 保存任务状态、短消息和文件引用。
- 对象/文件存储保存版本固定的大原文、附件和报告。
- Store 保存用户偏好与小型长期记录。
- 搜索索引保存可检索字段与原文版本引用。
- 临时执行环境只承载任务执行所需的副本。

### 6.4 上下文策略

先给模型来源索引，检索后取回少量窗口。每轮执行预算控制，并保留未完成任务与约束摘要。对证据冲突、引用失败和搜索截断设置显式处理路径。

### 6.5 写入与发布协议

不同工作单元写不同路径；报告生成后固定版本。使用 manifest 关联 source_id、原文哈希和产物版本。共享偏好通过版本条件更新或串行写入。发布状态与图恢复分开记录，避免重复交付。

### 6.6 监控与失败

监控 token、存储放大、工具延迟、检索完整性、引用失败和授权拒绝。对象上传成功但索引更新失败时，系统应能重建索引；任务恢复发现文件缺失时，应重新拉取或报告不可恢复，不凭摘要继续编造。

面试加分点是把这些选择与数量级、故障模式和验收指标连起来，而不是罗列数据库产品名。

## 7. 场景排障题与参考答案

### 场景 A：用户 B 看到了用户 A 的报告

排查顺序：线程访问授权 → Store namespace → Filesystem root → Composite 路由 → 检索索引权限过滤 → 缓存键 → 已存在的消息历史。修复后以两用户、两租户、相同文件名建立回归测试。

不要只换一个随机文件名作为隔离方案；不可猜测地址不等于授权。

### 场景 B：Agent 明明读了文件，却引用了旧数字

检查读取到的是哪个版本、分页是否跨版本、摘要中是否保留旧结论、证据索引是否过期，以及最终报告是否正确引用。记录内容哈希可以区分“模型理解错”与“系统提供了旧内容”。

### 场景 C：工具返回成功，但 grep 只找到部分材料

检查 truncated、max_count、时间预算、搜索范围、glob、权限过滤和字面量语义。将查询拆成更小范围，统计已扫描分区；不要用提高 recursion_limit 掩盖检索策略错误。

### 场景 D：程序恢复后重复发布了报告

检查发布节点是否可重放、是否存在稳定幂等键、外部发布完成状态是否与图检查点分离。通常需要可去重的提交协议；仅增加重试次数会使问题更严重。

## 8. 编码练习与验收答案

### 练习 1：分页拼接

写一个读取全文件的函数，限制每次最多 5 行，并检测下一偏移量不前进。答案要点：检查 error；使用 next_offset；以源行拼接避免重复添加换行；对空文件、末页和多字节文本测试。如果需要字节级恢复，不要用行读取接口代替下载。

### 练习 2：隔离测试

构造两租户、各两用户、各两线程，共八个请求上下文。答案要点：同用户不同线程的偏好可见；不同用户或租户不可见；草稿仍按任务隔离；每个身份只能访问自己授权的 thread_id。

### 练习 3：权限白名单

只允许写 `/output/**`，其他路径拒绝。答案要点：具体 allow 在前，兜底 deny 在后；测试 edit/delete 和父目录路径；说明直接 Backend/上传/执行入口需要另行控制。

### 练习 4：审计扩展

为包装器增加最大单文件大小和请求超时。答案要点：大小以实际编码字节计算；上传二进制也检查；超时不能仅靠函数返回后统计；同步/异步入口一致；失败日志不包含原文。

### 练习 5：Composite 故障

让一个路由后端模拟失败，确认聚合搜索不会被误解释为完整全集。答案要点：检查错误传播和截断；记录哪个分区未完成；报告中明确证据范围，不以空列表吞掉失败。

## 9. 最后一轮口述检查

不看讲义，分别用一分钟回答：文件系统如何节省上下文；State 与 Store 的区别；Filesystem 为什么不按线程隔离；工具成功为什么不代表证据完整；怎样防止并发覆盖；如何证明模型确实生成了可核验产物。

若某个问题只能回答出类名，回到对应实验，用实际输入、工具结果和存储状态重新解释一遍。
